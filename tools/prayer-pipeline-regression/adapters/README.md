# Current prayer pipeline prerequisite adapters

These five entry scripts run the protected Knowledge72, Dispatch55, Producers56,
Integration41 and Graph166 requirements against the current game sources. They
accept one absolute `raw.json` output argument. All new artifacts live in that
output directory or its `archives/`; protected suites, results and game data are
never rewritten. The parent orchestrator owns execution and evidence freezing.

`manifest.json` lists prerequisite adaptations and evidence classes by original
check ID. Its supplemental IDs add evidence; they never replace or remove an
original requirement. No source or gameplay implementation belongs here.

## Legitimate naming and relationship prerequisites

Old fixture-only calls to `_nominate_local` outside a Turn transaction now use
the original Attention identity reservation and `World.submit` standalone
nomination. These are current named prerequisites, not first-focus cohorts or
natural contact production. Identity-only reservations grant K, not P/N/F;
future fixed cards still pass the real P/N admission. Actual in-transaction
local expansion continues through the original method, unchanged.

Kinship and notice fixtures read actual current initial graph sources. They do
not insert family/support/cooperation or make a generic origin into a business
proof. The independent-patient and due-priority scenarios select a conditional
real graph in a declared finite 1..512 initialization seed search; chosen seed
and exact family sources are recorded. This is fixture selection, not a graph
frequency test or a claim that every campaign has these relationships. Original
assertion expressions, timing, costs and rejection expectations remain outside
the explicitly classified late-relation equivalence below.

The actual family ordering in Producers and Integration applies only while
running the PR01 action-window fixture. `_record_production` alone reuses the
first immutable formal run's seed 7919 order: NPC3, NPC5, then remaining sorted
people. Its first protected case still uses the later NPC5 record holder, and
its actual-dream case uses NPC3. Directed Integration matrix cells alone reuse
that published NPC3 dream prerequisite. Independent-witness, undirected and
other cases retain sorted identities. No assertion accepts an undirected result
as a directed result. The late-relation rollback baseline remains after actual
`end_actions`; only the rejected `advance` must preserve that baseline.

Automatic notice positives explicitly replace the old six-seed input. Before
any evolution, the fixed initialization-only search 1..512 selects the smallest
seed with the required real directional graph, retained local roles, first due
turn 2, and original cursor RNG-copy draws that select NOTICE from the complete
three-root pool APPEAL/PASSAGE/NOTICE. Valid and same-institution cases can have
independent seeds; each records every examined seed and rejection reason in
`archives/notice-initial-input-*.json`. No selected world is evolved to decide
whether to keep it, and no failed runtime world is swapped for another seed.
The sender must be the smaller retained identity so the initial real scan starts
with that known sender. This is a component fixture condition, not an assumption
of reciprocal support or coverage of all graph orientations. The required
sender-to-recipient head is read directly; family-only wrong-relation controls
must have no support/cooperation head in either direction.

The same-institution case retains its earlier legitimate separate passage
messenger. Both positive inputs retain actual dream recognition, the real
bootstrap, root competition, the twelve-round cap, and every original business
assertion. T1 must not consume the cursor or notice position. A pure read-only
pre-advance check at first due T2 calls the original option and notice readers
and compares the complete root list, known sender, exact directional source,
mode and copied RNG prediction. Complete eligible objects and order, full choice,
notice scan and every sample field must then match the actual committed tick
exactly; sample normalization is none. Its diagnostic sample describes the
pre-advance transaction base (current committed sequence and next_fact - 1).
Knowledge.capture outside a transaction still correctly returns empty. This
private comparison does not create source authority or a gameplay rejection.
It never submits that diagnostic selection or
sample to an authorization. A mismatch fails the prepared input before advance;
it does not start a new search. The committed selected/received/tick facts must
share the actual evolution receipt and match the predicted root pool, RNG and
mode. In particular, a focused T1 delivery cannot pass as a background delivery.
Every actual evolution advance still archives the full tick and separate frozen
and current observations in `archives/notice-step-*.json`.

## Late relation knowledge cutoff

The old Knowledge late-support assembly is no longer a lawful producer: it
writes a relationship directly after evolution without an actual business
authorization. Its exact inherited assembly is executed and must be atomically
rejected, preserving World, Turn and RNG. This is recorded separately.

There is currently no legal phase-four producer of new support/cooperation for
an already identified sender. Therefore the original legal-managed-fixture
claim is not retained. `PK-NOTICE/same_batch_relation` instead combines that real
rejection with an explicit predicate microprobe: an in-memory copy of the actual
Knowledge script controls only the identity-query dependency; a second copy
removes only the relation cutoff guard. A real graph relation must fail before
its cutoff, pass with a fresh cutoff, and flip to acceptance when only that guard
is removed. Both generated script bytes, hashes and exact replacement strings
are archived. No World knowledge/proof is altered; this is neither a legitimate
identity acquisition nor a managed notice run. Its class is
`mixed_runtime_and_predicate`, and the sensitivity supplement is
`counterfactual_probe`.

Passing this suite would prove the listed component requirements under their
declared prerequisites. It would not prove natural source closure, a playable
or fully restorable Session, a completed CULT implementation, campaign pacing,
or balance. Formal execution waits for the root coordinator's source freeze;
two consecutive formal failures stop the task for handoff.
