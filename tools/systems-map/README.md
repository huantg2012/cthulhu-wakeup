# 系统地图维护说明

本目录维护根目录的「邪神苏醒 · 系统地图」：一个供制作人理解游戏设计与世界状态变化的只读网页。**它不是游戏规则真相源，也不是已经接入 Godot 的实时跟踪器。**

## 1. 打开与文件分工

统一入口是仓库根目录的 `systems-map.html`。它加载本目录的本地脚本与样式，无 npm 安装或构建步骤。可以直接用浏览器打开；需要稳定预览与浏览器自动检查时，从仓库根目录执行：

```sh
python3 -m http.server 8767 --bind 127.0.0.1
```

打开 `http://127.0.0.1:8767/systems-map.html`；直接进入世界循环可加 `#world-trace`。端口已被本项目预览占用时复用原服务，不要随意结束其他进程。分享或移动文件时，须保留下面的相对路径，不能只复制 HTML。

| 文件 | 改什么时看这里 |
| --- | --- |
| `systems-map.html`（仓库根目录） | 全貌、整轮运行总图、顶层导航、公共主题、总图抽屉，以及内嵌的 `SETS`、`TASKS`、`NOTES`、`FLAGLIST` |
| `world-trace-data.js` | 世界状态类别、字段中文名、术语解释、来源、阶段约定、开局／中期教学轨迹、记录校验及前后快照 |
| `world-trace-view.js` | 观察点导航、全局说明、对象详情、搜索、追因、导入导出与阅读位置记忆 |
| `world-trace.css` | 世界循环布局、对象详情与阅读控件；颜色主要引用 HTML 中的公共变量 |
| `world-trace.test.cjs` | 使用 Node 内置测试运行器的回归检查，无第三方测试依赖 |

顶层只保留 **全貌 / 整轮运行总图 / 世界循环**。旧的五系统、深潜与实现状态页保存在 HTML 的 `retired-system-pages`、`retired-status-page` 两个 `template` 中，**不属于活动页面**。不要因搜到旧标题就误改为重新上线，也不要把它们当作当前用户看到的内容。

## 2. 更新前先确定事实来源

| 要核实的内容 | 真相源 |
| --- | --- |
| 当前设计规则、先后顺序、例外 | `docs/specs/system-*.md`，必要时查 `docs/architecture.md` |
| 数值、文明蓝本、人物原型、效果条目 | `data/*.csv` |
| 契约、任务编号与登记状态 | `docs/implementation/traceability.json` |
| 实际代码接线与执行逻辑 | `src/**`，不能用任务名称或规格中的目标能力替代 |
| 已验证什么、未验证什么 | `docs/qa/**` 中相关报告的范围与结果，不只检查文件存在 |
| 为什么修改或废止旧设计 | `docs/progress/decisions-log.md` 及 Git 历史；旧决定必须与现行规格核对 |

**网页不会自动读取或同步上述文件。** 例如教学蓝本、费用和效果是有来源的解释副本；HTML 中的契约与任务也是内嵌快照。修改 CSV 或任务状态，不会自动刷新页面。

不要恢复依赖会话外 `/tmp` 脚本的生成流程。本目录没有一键从全部规格重建网页的生成器；维护应直接修改对应源文件，并核对相关引用与测试。

## 3. 一次内容更新的顺序

1. **圈定变化**：是设计改变、实现状态改变、解释不清，还是纯界面调整。展示修正不得顺便改动 `src/`、`data/` 或设计规则。
2. **核实原文与边界**：同时记录条件、费用、数值、执行时机、留存及失效方式。设计与运行时代码不一致时明确标注，不自行拼成一种“已经实现”的规则。
3. **更新对应展示**：按下一节定位；同一事实出现在总图和世界循环时，两处都检查。
4. **更新演算与证据**：数值变化要检查后续所有观察点；更换报告时同时检查任务、范围、内容基线与 `provenance`。不能只改日期或基线号，就宣布旧例子已复验。
5. **增加或修正回归**：先从规则确认正确预期，再改测试。不要为了让测试通过而跳过不一致的前值或人口守恒。
6. **运行检查并实际点击网页**：具体清单见第6节。
7. **提交有限范围**：只暂存本次有关文件，不夹带浏览器截图、导出样本、临时日志或无关游戏修改。

## 4. 常见修改怎么做

### 4.1 解释某个概念

- `types[].meaning` 是**类别说明**，不是某条记录的实际属性。比如列举“病危、契约义务、异常记录”，不能让读者误认为当前人物同时经历了这些事情。
- `labels` 提供实际字段的中文名称；增加展示字段时同步补标签。
- `weaknesses`、`attentionRoles`、`clockExample` 存放已核实的概念释义；对象内说明由 `renderEntityGuide()`、字段提示由 `fieldHelp()` 呈现。
- 对象字段、引用及变化记录才代表这份样本此刻有什么。说明应明确区分**类别举例 / 本例状态 / 条件假设 / 尚未实现**。
- 优先讲“它管什么 → 条件与过程 → 结果和留存 → 例子与反例”，原术语和报告放到可展开区域。设计意图没有明确出处时，写成解释性理解，不当作作者原话。

### 4.2 修改开局或中期观察点

主要入口为 `opening()`、`middle(n)`、`buildWorld()`；共用构造工具为 `entity()`、`fact()`、`builder()`。

- `record.initial` 是片段开始前已有的数据；后续每个 `step` 依次读取前一步结果。
- 用 `builder.step(meta, write)` 添加观察点；在写入函数中使用 `w.add()` 新建对象、`w.set()` 更新已有字段。它们记录原因并生成可追踪差分；不要绕过这些入口直接改状态。
- 每步补齐 `title`、`lead`、`turn`、`phase`、`source`、`read`、`skipped`、`transient`：说明依据、实际写入、没发生什么，以及哪些仅是临时计算。
- 轮号与阶段必须按序；同一阶段可有多个观察点。提交检查点不是额外的第七阶段。
- 中期例子的期限与冷却由 `n` 推导，不写死某个轮号；调整 `n` 是平移教学坐标，不是从开局运行到该轮。
- 改变一个对象后，检查后续前值、人口三个口径、收入资格、费用、来源引用和终局条件。不要只改叙述而保留旧差分。
- 新增或移除观察点时，检查 `data-jump-middle` 等位置跳转、测试的快照索引，以及说明中“第几个观察点”的文字。

当前 `DEMO-*` 身份、初态与选定结果是教学实例，不是引擎采集日志。没有采集的种子或随机状态保持 `null` 并说明原因，不填一个看似真实的值。

### 4.3 修改总图与页面导航

- 总图节点的 `data-t` 是标题／说明匹配键；`data-d` 是短说明；`data-sets` 指向内嵌契约。改名时检查 `NOTES` 与筛选逻辑中的同名引用。
- `SETS`、`TASKS`、`FLAGLIST` 都是手动维护的展示快照。更新时核对追踪源和报告，不能把设计完成等同于玩法已验证。
- 世界循环的 `sections` 是页面级阅读范围；`views` 才是当前观察点下的不同视角。整局路径和接口说明必须在时间轴之外，不要在每个步骤下重复展示。
- `goTab()` 负责顶层切换；保留旧名称“分层模拟”到“世界循环”的迁移、无效旧页签回退，以及 `#world-trace` 初次加载／同页跳转行为。
- 新增内容必须放进正确的活动 `.page` 内。仅检查 HTML 标签数量平衡不够：曾有卡片位于页面闭合标签之外，导致切页后仍残留。

### 4.4 修改样式

保持日间主题、宽布局与小侧边距。公共色值改 HTML 的 CSS 变量；世界循环具体布局改 `world-trace.css`。说明栏应支持点击外部、失焦、Esc 和切页关闭，内部点击不误关。

不要用颜色暗示未经核实的模拟规则，例如把“回应祈求”染成“只有重点域才发生”。域的精度、人物的详细覆盖及共享结算是不同维度。

## 5. 数据格式与未来接入

目前展示记录为 `schemaVersion: 1`。浏览器加载 `window.WorldTraceData`；Node 测试通过 `require()` 使用同一份数据模块。

| 层级 | 主要内容 |
| --- | --- |
| 记录 | `kind`、`title`、`description`、`anchorTurn`、`provenance`、`sources`、`initial`、`steps` |
| 对象 | `id`、`type`、`label`、`domain`、`fields`、`refs`、`source` |
| 观察点 | `turn`、`phase`、`title`、`lead`、`scope`、`source`、`read`、`skipped`、`transient`、`changes` |
| 新建差分 | `op: create`、`entity`、`reason` |
| 更新差分 | `op: set`、`id`、`field`、`before`、`after`、`reason` |

`phase` 的0表示初始化，1–6表示正式阶段。当前差分只支持新建与更新，不支持删除操作；死亡、关闭和资格撤销通过状态表达，身份与历史不直接抹掉。若未来需要新操作，须一并调整 `validate()`、`snapshots()`、渲染器及测试，不要默默忽略未知操作。

`kind` 区分 `rule-walkthrough`（规则演算）与 `runtime-observation`（实机采集）。`provenance` 应明确来源、基线、覆盖范围与缺失项。标成实机采集不意味着网页已验证其真实性；仍需游戏侧采集器和集成证据。

当前文件导入限制为2 MiB；每片段1–200个观察点，展开后的对象不超过2000个，且对象数与观察点数乘积不超过100000；还有深度、字符串等安全限制，具体以 `safeValue()`、`validate()` 为准。

`validate()` 检查结构、顺序、更新前值与对象引用，**不等于证明游戏规则正确**。人口守恒、具体效果等由专门回归覆盖。导入失败保留原记录，文本必须转义，来源链接维持本地允许路径校验。

未来实时化应让游戏侧输出实际状态、提交差分与来源，再适配此格式；不要在网页里另写一套“猜测游戏会怎样”的模拟器。破坏性格式变更须明确升级版本并决定迁移或拒绝旧文件。当前仍能识别旧时钟字段名称，但新教学数据只写一份 `nextSlot`，不要重新制造两个独立时钟。

## 6. 提交前验证

从仓库根目录运行，需要能够运行 `node:test` 的 Node 环境：

```sh
node --check tools/systems-map/world-trace-data.js
node --check tools/systems-map/world-trace-view.js
node --test --test-reporter=spec tools/systems-map/world-trace.test.cjs
git diff --check
```

编写本说明时共有28项测试，覆盖人口守恒、回应效果、后台成员行为、单一机会时钟、域命名与蓝本对应、来源链接、导入拒绝等。以后以实际输出为准，不能把本数字当成永久验收标准。

浏览器还须实际检查：

- 顶层只有三个页签，每次只有一个活动页；旧页签记忆与深链接正常。
- 开局和中期每个观察点都能前进、后退，概览、字段与差分相互对应。
- 全局说明没有时间轴；返回后观察位置不变；全局说明中方向键不暗改步骤。
- 对象引用、中文搜索、筛选、历史跳转能用；说明可以收起查看数据。
- 详情栏内部可操作，点击外部、Esc、失焦、切页能关闭。
- 调整中期 `n` 后期限同步；合法记录可导入导出，错误记录不覆盖原状态。
- 常用窗口宽度下没有页面级横向溢出；宽表局部滚动正常；日间主题文字清晰。

例如使用已安装的 Playwright CLI 启动独立检查会话：

```sh
playwright-cli -s=systems-map-check open 'http://127.0.0.1:8767/systems-map.html#world-trace'
```

按实际页面快照操作并核对结果；结束后关闭该检查会话。截图结论必须在打开截图后再给出，不能凭文件生成成功就声称版面正确。

页面缓存或阅读记忆导致定位不一致时，先强制刷新。确需重置本工具时，只清除它的两个键：`cthulhu-systems-map-tab`、`world-trace-view-v1`；不要清空整个站点存储。HTTP地址和直接打开文件的浏览器存储可能不是同一份。

## 7. 提交范围与维护边界

- 用户请求提交后，在当前合适分支提交具体文件；先查看 `git status` 和暂存区，避免夹带他人工作。
- 常见交付为根 `systems-map.html`、本目录的四个代码／测试文件和本说明；是否全部暂存取决于本次真实改动。
- 不提交本地服务日志、临时截图、导出 JSON 或 `.playwright-cli/` 测试产物；只清理自己本次创建的文件。
- 此工具更新不代表游戏实现通过验收，也不授权改框架层。提交与推送分开，只有获得相应请求后才执行。
- 页面是可读解释，不是设计案的替代品。尤其要持续区分：类别与实例、规则与本轮结果、预留与正式成员、已有记录与过去亲历、条件演算与自然可达证据。
