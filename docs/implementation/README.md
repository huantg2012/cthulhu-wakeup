# 实施追踪与结算保障

这是本游戏的实施记录，不修改通用 agent 框架，也不增加短体验前置阶段。规则正文仍归各系统 spec，数值和内容仍归 CSV。`traceability.json` 只登记关键行为、权威来源、结算归属、开发责任与可观察验收，不能独立修改玩法。

## 每次实施的入口

### 模拟粒度优先（制作人 DEC-026）

默认用少量状态条件、权重、冷却及必要的概率修正抽取情境，一次登记需要的参与者、对象、期限和结果。正式抽签产生的情境就是游戏事实；可追溯只要求能解释这次生成与实际后果，不要求把每个背景环节做成模拟系统。

- 普通事故、关系背景、共同见闻、争议和契约缘由可以由情境抽签概括。不得默认追加职业日程、事故经过、传话、逐人签署或阅读链。叙事不能把抽签概括说成已经运行了这些过程。
- 只持续保存会改变玩家选择、资源、重要人物、材料、进展或后续事件的状态；其余背景留在情境中。已有事实不能被新抽签冲掉，死者不能重新求告，复制材料不能冒充第二份独立证据。
- 具名关系网继续采用已确定的网状结构；普通祈求不必逐次证明一套既存亲属、职业及接触链。涉及玩家已经建立的关键关系才沿用对应状态，不能为制造来源反过来加通用门槛。
- 新增持续状态、独立时钟或模拟步骤前，先写清它会改变哪一种玩家决策或可观察后果。说不清就并入一次情境生成。不能因旧代码或旧测试已有细节而继续扩建。
- 验证围绕少量玩家可观察结论。允许控制随机数来验证正式生产与结算，不直接注入目标结果充当生产。默认跑受影响的短检查；不逐小任务重复全量矩阵、反向搜索数百种子，或为无玩法收益的历史证明另建审计链。完整回归只在共享接口风险实际需要时运行。

事件规则§14.5是来源生成的当前目标。旧精细事故实现未验收，后续由五个SOURCE父任务替换；13个细化实施子任务撤销拆分，合回父任务；另14个进展操作/界面细分合回PROGRESSION-OPERATIONS、保存负例合回CULT-SAVE-COMPAT，均不计为完成。现有基础模块不在本次设计调整中整体重写。

### 测试从简，只守核心与本次风险（制作人DEC-026补充）

维护一套小型共享核心检查：加载/回合推进、资源与名额、正式生成到可回应及实际结果、关键期限/一次性结算、保存继续。修改共享核心时跑它；普通内容或单族变化只跑被影响的部分，每任务默认补2–4个直接相关的代表用例，普通快速批次目标不超过60秒。少量用例中的实际后果必须成立，不以文件存在/函数被调用/加载成功代替能力。

不默认铺全组合、全人物/文明矩阵、数百种子搜索、联合重签伪造或历史规模扫描；不逐小任务重复全量回归，也不为每项另建执行框架、授权账本与大批归档。优先复用现有工具、控制随机输入；只在共享边界实质改变、实际回归疑点或发布候选时扩大检查，并说明要覆盖的具体风险。真实Bug只补能抓住它的最小回归例。

自然轨迹与平衡选择少量代表情境，罕见事件的功能用受控抽签验证，不为偶然未抽中反复长跑。用例少不表示放宽资源、身份、重要材料、期限和一次结算；被制作人撤销的微观过程断言则不再追着修。

本轮必须先读 [整改原则与计划](correction-plan.md)。2026-10-27 核查确认：严格来源凭据仍可能维护错误玩法前提，消费端测试通过不代表生产职责已经实现。问题先分世界观方向、系统设计、实现缺陷与数值调优；详细/后台切换核对职责交接。新增实现须分别说明声明、正式生产/调度、消费后的可观察结果和自然可达证据；后三者不得用文件存在、函数名或手工注入目标代替。首批快速检查由 TASK-CAPABILITY-GUARD / PROBES / AUDIT 承接，限定候选生成职责的正式接线、短行为与少量能力核查，实际状态和运行证据见追踪源及 docs/qa/capability-guard.md、capability-probes.md、capability-audit.md。检查共用正式执行绑定并对照CSV声明；未覆盖职责、自然频率和任意自然语言声明仍须独立判断，不能因为本条存在就宣称全项目具备自动防漏能力。

0. **方案新增或修改必须在同一轮编入开发计划**（[DEC-017](../progress/decisions-log.md#dec-017--方案变更必须当轮同步开发计划)）。这也适用于只做方案、不开发的会话：完成任务拆分／调整、前置与下游影响、关键行为与验收、路线／当前工作及工作台同步；允许任务仍为 planned，不允许把“以后再编计划”当收尾。
1. 先运行 `python3 tools/implementation/check.py`。结构错误必须修复；未实现、未验证是如实记录的工作，不得为了让报告变绿删掉。
2. 用 `python3 tools/implementation/check.py --impact MECH-PEOPLE`，或 `--impact data/npc_profiles.csv`，取得直接要求、结算约定、开发任务、下游受影响任务和应读来源。`--task TASK-NPC-ACTIONS` 同时检查前置证据。前置缺失可做设计准备，不能把依赖占位物当已验收能力。
3. 读任务对应的唯一 spec、CSV 和有关讨论。对照 `given / when / then` 确定此次要产生的可观察结果；写代码前解决取样时点、状态写入责任和同轮冲突。不能只靠工作台摘要实施。
4. 实现只在任务声明范围内。跨域共享状态经归属结算入口修改；先定约定再并行，其他任务以事实/请求交互，不分别维护第二套状态。
5. 跑本任务场景及影响分析列出的回归。新证据必须带稳定检查编号、运行时间、规则/CSV/实现/测试源码 SHA-256、实际结果和限制。未运行的场景不得填 PASS。
6. 收尾逐项登记实现和证据；保留未知、失败和过期项。更新工作台摘要、复核来源后才更新 game-state 基线。基线不会更新证据或任务状态。交接必须包含目标、要求/任务编号、变更、命令、结果、未决项与下一步。

## 能力表述必须与证据相符（DEC-021）

适用于对话、交接、spec、任务、展示台和报告。先核实再描述；不知道就写未核实，不用叙事补出能力。规则写入只建立人工执行要求，不代表已有自动语义审查器。

- **说清具体运算与边界。** 聚合人口计数称聚合招募；资格记录称资格判断；指定材料的递交称材料递交。未模拟逐人接触、渠道覆盖或传播过程，就不得称已模拟人际传播网络。“真实/完整/自主/动态/闭环”等词不能代替对象、状态变化与证据。
- **分别标明设计、代码与验证状态。** 已提出/已写设计、已接入代码、限定场景已验证、自然新局已验证是不同结论；未来时态也不能夸大设计粒度。报告以当前范围为主句，限制写在相邻位置，不用末尾一句“尚待验证”挽救前面的扩大声明。
- **证据不能跨层借用。** 对象/事实存在只证明来源可引用；函数、文件或调用存在不证明产物；消费夹具不证明生产；聚合结果不证明个体过程；一次有限检查不证明完整能力。声明不得比所引用的设计或证据更强。
- **发布前逐条对照。** 对本次新增/修改的能力说明，核对对应规则/代码/实际检查，写明模拟粒度、输入输出、未覆盖行为及未实现部分。人工或独立审查发现不符时，先纠正原句及下游摘要，保留原报告并加显著勘误，检查旧结论是否仍成立；不靠补一个接口名维持原声明。
- **本次反例。** 禁用“真实本地生活圈/渠道运作”描述当前cell。准确说法是“目标设计按教团成立、领袖/成员状态判断招募资格，再从本域无名人口池按公式聚合招募；不模拟社会接触网络，旧运行时仍待接入”。不得据此推断招募对象已经逐人知晓邪神。

通用规则回流由TASK-FRAMEWORK-LESSONS单独在master实施；本轮只改本游戏执行入口。该任务须同时处理措辞夸大与实现遗漏，不能认为有生产探针就能自动证明所有自然语言声明。

## Task 完成后的提交约定

按作者 DEC-018，后续每完成一个 task，必须把该任务的实现、必要的规则／数据、验收证据、计划与工作台同步作为一个完整提交保存。先完成适用检查并如实登记状态，再检查暂存范围并提交，交接时报告提交号；不得累计多个已完成 task 等待统一提交。未通过验收的工作不能为了提交而标记 verified；如果任务只交付方案，仍须遵守 DEC-017 当轮编入计划。

本次将已有未提交工作汇总成一个基线提交；此后按任务执行。只提交本任务应有的变更，保留其他未完成工作的独立范围。提交不等于推送，未获得推送要求时不自动推送。该约定只作用于本游戏，不修改通用框架。

## 四类稳定对象

- `REQ-*`：关键行为要求。包含能力/关系/作者决策、规则摘要、权威来源、责任任务与验收；不以“人物系统完成”吞掉死亡、迁移、继任等细项。
- `SET-*`：跨系统结算约定。明确事实归属、读取输入、唯一写入、阶段、前提、冲突顺序及不变量。规则正文在对应 spec；列表是可检查的责任索引。
- `TASK-*`：可核验的工作责任。记录前置、范围、交付物、限制、风险和验收。`planned / in-progress / implemented / verified` 分别表示计划、进行中、实现接入和已验证。
- `ACC-*`：给定条件、执行动作和预期后果。绑定报告中的真实检查编号；手工体验验收同样必须另有真实记录，不从自动测试推定。

工作台支持以上对象的稳定链接和讨论。讨论“已回应/待落实”不会修改设计接受状态、开发状态或验收结果。设计细节默认仍是可迭代提案；用户授权实施不等于对每个数值的永久终审。

## 方案与计划同步约定

这项约定适用于本游戏项目，不修改通用 agent 框架。每次完成新增方案或原方案修订，必须同时完成：

1. 明确变更范围、采纳／提案状态及受影响系统；规则原地更新，技术提案明确待迁入哪些有效 spec。
2. 在 `traceability.json` 新增或调整 REQ／SET／TASK／ACC。任务必须有责任、范围、依赖、交付与可否证验收；接到真实下游，不能只追加一个无人依赖的任务名。
3. 将变更写入当前工作、路线和相应任务书；被替换的旧“下一项”与风险排期同时修正。暂缓方案也要给出明确责任、排期／进入条件及原因，不能无主悬置。
4. 核对既有证据范围。计划登记不等于完成，修改了验收所依据的规则则保留过期状态，直到后续真实重新验证；不得刷新哈希伪装旧结果适用于新规则。
5. 更新工作台来源与能力摘要，检查通过后复核基线并重建离线页。非实施会话只运行必要的计划／制作工具检查，不因此自动启动游戏功能开发。

追踪源的 `planBindings` 保存每份方案的 `source`、`sourceHash`、关联 `requirements`／`tasks` 及 `reviewNote`。维护者完成上述语义核对后才更新 SHA-256 和影响说明；不提供批量自动“修复指纹”来替代排期。

机械门槛扫描 `docs/vision.md`、`world.md`、`gdd-core.md`、`architecture.md`，`docs/specs/**/*.md`、`docs/content/**/*.md`，以及 `docs/implementation/*.md` 的方案文档。`_template*` 是框架模板，实施 README 是操作协议，均排除；`docs/ori/`、`docs/qa/`、进度记录、任务书及派生视图分别是历史、证据、计划或输出，不再作为另一套方案正文。新增独立技术提案统一进入 `docs/implementation/`；新方案门类必须先扩充扫描范围。

扫描到未登记方案、源文件已改变却未复核、无效任务／要求、没有实际验收连接或越界来源时，普通检查报错，工作台沿用同一错误。文件指纹只能证明绑定的是这版文本，不能证明自然语言影响已全部识别；“只改措辞、无实施影响”也必须给出具体复核说明，可保留原任务，不强迫每次新增任务。

## 机器检查能保证什么

检查引用、能力覆盖、任务依赖无环、共享事实归属唯一、场景有消费者、交付物与完成声明一致。所有登记验收的证据必须存在、包含对应检查，并绑定场景规则来源；来源发生变化显示过期。检查失败、来源缺失、没有运行都不能冒充通过。

`--strict` 只有所有登记场景有当前通过证据且无未分配任务时才返回 0。普通检查允许未来任务尚未验收，方便持续开发；它会明确给出缺口数量。退出码 1 表示结构/声明错误，2 表示严格验收缺口或任务前置未通过。

机器不能自动证明自然语言已经穷尽、因果解释充分、所有选择没有通解或故事好玩。修改 spec 中既有段落未必增加文件，因此每次收尾仍须人工/独立审查关键行为覆盖。新增能力、删除要求和降低验收条件都必须解释原因；不可通过弱化断言解决失败。

## 开发顺序与游戏关系的区别

`REL-*` 是玩法作用关系，允许循环；`TASK-*.dependsOn` 是实施前置，不允许循环。已完成正式数据、身份、随机/存档、有限推演及回合／经济的限定范围；当前插入分层模拟七项任务，再接回教团、权能、锚点、事件与终局。基础推演中的锚点失效处理只证明该项联动，不能据此把完整锚点建立/供奉任务勾完。

具体任务正文见 [分层模拟任务书](../tasks/slice-04.md)及 [基础与后续工作责任](../tasks/slice-01.md)，当前范围见 [当前工作](../progress/current-slice.md)。这些文件引用追踪记录，不另存一份相互竞争的任务状态。

## 真正未决事项与 task 收尾（作者本次要求）

唯一结构化登记是 [residuals.json](residuals.json)。已有真实后续任务及其验收承接的工作放在 `taskReviews.planned`，不计入遗留总数；普通 planned task、未验证场景、尚待完整游戏检验的平衡问题不自动变成 issue。历史 backlog 仅作解释/来源，工作台与门槛均读取这个登记。

真正未决保存在 `items`，使用稳定 `ISSUE-*`：分类为 `unplanned`（无计划承接）、`decision`（需作者裁决）、`blocking`（实际阻塞）。每条须写来源 task、负责人、具体问题、下一动作、来源文件、状态和被阻塞任务；分类可与阻塞关联并存，统计阻塞项按并集去重。无须为了填表创造待决事项。

每个已完成 task 必须有 `taskReviews` 收尾记录：人工核查其实际范围、风险、非范围、QA限制与后续任务；明确 planned 交接、issue 编号，或明确没有。交接须指向真实任务及属于该任务的实际验收编号。`reviewedTaskHash` 固定 scope/acceptance/deliverables/risks/outOfScope 的审查版本，变化后要重新核对；禁止无语义复核自动批量刷新。机器只能检查已登记内容，不能发现所有自然语言遗漏。

无审查不能标 verified。真实阻塞会使关联任务和依赖它的下游不可开工，被直接阻塞的任务不能假完成；不相关的工作可继续。需要作者裁决但不阻塞的事项仍列入统计，由其负责人明确提出问题，不把静默视为批准。

关闭条目保留历史，必须填写解决说明和来源依据；未规划事项转入计划时还要登记实际承接任务及验收。决策依据应链接作者确认记录，修复依据应链接真实验证；文件存在检查不代替语义审查或自动批准。普通登记文件损坏/缺失、字段错误、假任务引用或漏列 issue 时普通检查报错，工作台显示“不可判定”，不能把读不到当零。

收尾顺序：复核 task → 交接或登记真正未决 → 跑追踪/受影响检查 → 同步工作台 → 提交。该机制由 `TASK-RESIDUALS` 验收；后续每项游戏任务沿用，下一工作以 [当前工作](../progress/current-slice.md) 和追踪源为准。
