审查对象：[ui-experience.html](../game-state/ui-experience.html)，SHA-256 `98565e949571310c47e814d8e38b73f3b1257ccdcf97c9bda46c2d107eec3978`。本轮仅审查与留档，没有修改原型，也没有把评审建议登记为制作人已批准决定。

**结论：共同布局值得保留，完整游戏体验尚未成立，不建议进入视觉制作。** 已补上大部分功能入口，但一些真正影响选择的信息和关系没有进入结构，且存在行动草稿与预算预览错误。上轮“完整覆盖游戏流程”的交付措辞过满，应收窄为“主要功能入口与部分流程已经可走查”。

依据为制作人的实际需求、原型源码、正式 ActionCatalog/选源代码和玩法参数，并对关键路径作只读 DOM 复现。没有使用 in-game-ux 或旧美术规范。浏览器访问当前本地文件被 URL 策略阻止，未绕过限制；本报告不评价实际像素排版、文字大小、遮挡或美术质量。

## 值得保留的部分

- 顶部全局、两侧主体、底部权能与编年史、中央当前任务的共同框架。
- 世界入口独立于教团，能找到没有教团的已知世界。
- 教团全体具名成员入口，且与无名信众分开计数。
- 教团、圣物独立滚动与查名，完整权能保持稳定顺序。
- 最新编年史常驻；事件临时获得中央优先；轮末有单独检查位置。

## 核心问题

### R01 · P1 · 行动目标与返回过程不可信

**复现一：**选世界04的教团，从底部打开赐予，默认人物却为世界01的N01；最终预览没有列出目标姓名或世界。当前主体与实际目标脱节。

**复现二：**入梦准备 → 入梦预览 → 查看全局安排 → 教团 → 人物 → 发动权能 → 赐予预览；取消并逐层返回原入梦预览，原表单仍属入梦，但待执行项与预览已变为赐予。全局单例 `pending` 被第二个任务覆盖，取消不恢复原任务。两条均已作DOM复现。

**影响：**复杂游戏需要玩家查资料、做准备后回到原决策；当前这条基本路径会使目标或行动被替换。

**修正方向：**从主体继承合法上下文，缺少明确目标时要求选取；提交位置固定显示行动者、对象、世界、关键媒介。每项行动的草稿与预览归属于自身任务，关联查看与另一行动不能覆盖它。

证据：[app.js](../../tools/ui-experience/app.js) 的 `formOptions`、`previewBody`、`dispatch('preview')`、全局 `pending`。

### R02 · P1 · 费用没有接到持续责任上

**DOM复现：**默认中期局面准备赐予，预览显示花6信仰、剩12；打开“查看全局安排”，仍按付款前18信仰显示无供奉缺口。执行后再查看，末位宇宙锚点无法支付，预计苏醒减少10。

**影响：**支付与供奉各自有页面，却没有共同支持“现在花这笔钱是否值得”的核心判断。不是演示数值精度问题，而是关联页采用了错误的状态。

**修正方向：**预览区分现在与执行后的假设状态，直接指出受影响的具体教团/锚点与苏醒变化；关联供奉页沿用同一假设。调整计划后刷新比较，不提前执行行动或收费。

证据：[app.js:101](../../tools/ui-experience/app.js#L101) 的 `budgetBody` 与 `previewBody`。

### R03 · P1 · 祈求没有形成可以判断的具体处境

**复现：**默认局面查看“不要让她死去”，能看到费用和通用收益，却看不到“她”是谁、与求告者的关系、病危期限，以及它与请求窗口的区别。各祈求统一指向 `S.people[0]`；准备回应还可以任意选择其他世界的人物。

**影响：**玩家难以比较祈求的紧迫性、价值和持续后果，且会误以为回应允许任意更换主体。正式接口已提供原危机对象、求告方向、请求期限和危机期限，当前结构没有接住。

**修正方向：**先展示事件涉及的人物和关系、当前局面、两种期限，再比较浅触/深应；固定原求告者，真实代理成立时才提供代理选择。无需先补文学文案或美术。

证据：[app.js](../../tools/ui-experience/app.js) 的 `prayerList`、`prayerBody`、`prayerSetup`；[action_catalog.gd:34](../../src/presentation/action_catalog.gd#L34)、[entry_selectors.gd:291](../../src/game/entry_selectors.gd#L291)。

### R04 · P1 · 实际活动被压成18项通用目录，缺少进行中的事情

**复现：**初醒只有一个未入团人物，也列出全部18项“当前活动”。共同见闻、互惠交付、祭仪教习都进入近似的“人物、另一人、来源”表单；材料页固定显示完成1/2回合。

实际共同见闻需要额外三名参与者；互惠有两端记录和原约定；教习涉及原学徒另一轮独自施行。正式选源也按文明、角色和当前来源限制入口，已有逐项跨轮进展投影。

**影响：**玩家无法看见自己正在维持哪件事、原参与者是谁、下一步何时由谁完成。初期还被迫从全游戏目录里自行辨认哪些与自己有关。各活动是否有按钮，不足以证明机制体验覆盖。

**修正方向：**人物/教团优先呈现正在进行、当前可推进、还缺条件的具体事情；不同活动保留自己的关键对象与步骤。完整权能目录继续可查，不通过隐藏权能来解决此问题。

证据：[app.js:103](../../tools/ui-experience/app.js#L103) 的 `routesBody`、`materialsBody`、`routeBody`；[entry_selectors.gd:219](../../src/game/entry_selectors.gd#L219)、[action_catalog.gd:191](../../src/presentation/action_catalog.gd#L191)。

### R05 · P1 · 风险预览有概率，却没有同位置的各档后果

**复现：**播种进入最终预览，列出四档概率，但“可能变化”主要采用成功收益；失败人口损失、灾变的更大人口与凝聚损失没有与概率并列。锚定灾变封存圣物的后果也没有在提交处展示。准备页的折叠说明不能替代提交时的判断。

**影响：**此类游戏的核心风险取舍被拆散到不同层级。即便替换为真实概率，该结构仍不足以支撑决策。

**修正方向：**必付代价与四档各自后果分清；共同结果可合并，主要收益和不可逆损害须在提交处可读，相关对象可追查。

证据：[app.js](../../tools/ui-experience/app.js) 的 `powerBody`、`makePlan`、`previewBody`；[powers.csv](../../data/powers.csv)。

### R06 · P2 · 多区域框架在操作时失效，普通查看也全部阻断

世界、人物、圣物、权能准备和预览共用同一张替换式详情窗口。`syncModal` 将顶部、两侧、中央、权能和编年史全部设为不可操作。查某人携带圣物后，要比较另一人或另一物件，仍需沿链接深入或退回多层。

**影响：**认可的布局提供了全局骨架，但高频操作没有保持多主体对照，记忆负担仍由玩家承担。这是交互结构问题，不取决于是否使用美术。

**修正方向：**事件与重大确认可继续阻断；普通资料和行动准备与当前主体并置，或保留一个可操作的对象索引/对照位置。当前不需要扩展为复杂的自由多窗口系统。

证据：[app.js](../../tools/ui-experience/app.js) 的 `showSheet`、`renderLayers`、`syncModal`。

### R07 · P2 · 祈求注意力与阶段变化仍不一致

未回应时进入教团，主场景不保留待处理数量、剩余回应机会和最近期限，底部只剩普通“祈求”按钮。已回应时反而有状态横条。初醒回应后，因为没有教团，中央继续显示完整只读祈求卡，人物及剩余操作排在后面；此路径已作DOM复现。

**影响：**未完成核心任务容易消失，已经不能操作的任务却继续占据优先位置。

**修正方向：**未回应时以紧凑摘要保留待处理数量、机会与紧迫期限；已回应后所有阶段统一收缩，中央优先交给仍可操作的人物或教团。

证据：[app.js](../../tools/ui-experience/app.js) 的 `renderChronicle`、`renderStage`、祈求执行后的 `S.center`。

### R08 · P2 · 容量已考虑滚动，但对象范围与存量含义未收好

- 解离R04后，常驻圣物仍显示18件，已消耗物继续混在当前库存。长期积累会让历史条目挤占高频列表。
- 从世界01教团“查看护持与媒介”，会显示世界07和11的锚点，传入的当地ID未用于筛选。
- 人物“已知经历”传入人物参数，打开后仍是全部编年史。

上述前两项已作DOM复现。完整世界入口、全员名册、滚动本身成立；需要修的是“当前拥有多少”“这个对象有什么”的范围可信度。

**修正方向：**局部入口默认局部范围并提供查看全部；全局入口才默认全局。当前资产与历史身份分开筛选、明确计数，不能靠继续增加滚动容量解决。

证据：[app.js](../../tools/ui-experience/app.js) 的 `renderRelics`、`cultBody`、`anchors` 分支、`personBody`、`historyBody`。

## 对验证与下一批工作的建议

现有25项检查验证了部分按钮、状态和样例结算。18路线检查仅验证页面存在且文字长度大于20，不能证明必要字段、条件、进度与前后任务衔接。现有报告保留其原范围，不删除或改写成更强的证据。

建议下一批保持现有外框与灰阶，只把一个中期连续任务做实：比较具体祈求 → 查看关联教团和全员 → 为目标人物准备行动 → 看清四档后果及行动后供奉缺口 → 调整安排 → 返回原行动并执行 → 查看下一轮的具体变化。优先修R01/R02等可信度问题，借此验证R03–R07的结构；其余机制先保留入口与待验证标记。此为评审建议，尚不是制作人批准的新制作批次。
