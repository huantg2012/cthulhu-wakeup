# 关键机会共享合同：制作人报告

本批完成 **TASK-OPPORTUNITY-CONTRACT-DESIGN** 的设计与静态验收，不包含游戏运行实现。父任务 TASK-PROGRESSION-ROUTES 仍在进行：首团、八类文明、终局共十个目标，至少二十条具体路线分三批接续设计。本批没有把这些路线算作完成。

发现并处理了三个设计问题：

1. **提高概率仍可能一直等不到。** 方案保留普通抽样的概率补偿，连续两次合格机会未派发后进入强制队列。普通落空、被其他事件选走、查询还没扫到，均不能当作“暂停等待”。真实缺人口、资源或容量则记录具体原因；没有释放条件时不能承诺日历截止。
2. **抽到来源不代表玩家拿到了机会。** 选源后还要经过固化、展示和行动资格检查。只有玩家能看见、至少一种做法现在付得起，并有完整行动窗口，才记作已经给过机会。预览、内部对象存在或开局预检都不算。每条后续路线必须证明整段交付最多要多久，或者提供合法直接行动；不能填写一个等待数字冒充证明。
3. **失败者反复回到队首会饿死其他目标。** 派发一次就用掉本次排队票；之后失败仍保留等待记录，但合法重试拿新票排到队尾。提交前刚失格、没有产出的候选也不能耗掉整次机会；同次有界重查要让当前合法者继续参与。未提交的事务失败才整体回滚。这区分了“不清掉等待”与“永远拥有优先权”。

身份未知/已知、重点/后台四种情况共用目标和等待记录；只有具体行动原本要求时才检查身份知晓或关注。补偿不会凭空生成旧关系、独立见证、材料或献身意愿，也不保证回应成功、首团成立或胜利。原期限、固定人物和容量继续有效，等待记录不能替代三轮断联规则里的真实接触计划。

正式数据新增六项参数和十类目标清单，全部目标标为 `design_only`，尚未被运行时装载。规则原地写入 `docs/specs/system-events.md` §14.8、`docs/specs/system-progression.md` §12。共享状态/派发票/服务回执/版本和保存由 SET-OPPORTUNITY 登记唯一责任，正式接入归 TASK-OPPORTUNITY-SCHEDULER，并交接源闭合、完整存档、自然验证和节奏调优。

实际执行 `python tools/opportunity-contract/verify.py`：九项静态检查通过。有限模型枚举五种排队位置和四种首槽相位，共二十种情况；另有反复失败重试，以及允许插队/移除强制机制的负例。既有十二域、每域三个机构推得全局最多三十八个目标实例、每域最多五个竞争项。在同一目标持续合法、没有真实阻塞的条件下，模型的 B 派发保守上界是二十八轮。**这不是首团节奏目标，也不是实际可行动机会的服务上界。** 后继管线界 L 仍待具体路线证明，工具输出 L 和实际服务上界均为空；没有运行第二份游戏调度器，也未执行实际提交前失格重查、handler事务或回滚行为；这些归正式调度任务验收。

独立静态审查核对了真实输入起计、四种情况共债、实际行动窗口、队票公平、保存与下游归属。检查不证明正式生产、完整新局、自然可达或真人体验。本轮原有源码、旧数据及历史 QA 共二百三十五份保持原字节，旧报告不重签。OPPORTUNITY-PLAN 仅在本轮新报告复核当前任务责任和原规划时点；社会图两项旧证据因共享来源变化继续显示过期，后续路线开工前须新静态复核。原 Catalog 根语法与 CULT 兼容阻塞保留，两个原问题未关闭。
